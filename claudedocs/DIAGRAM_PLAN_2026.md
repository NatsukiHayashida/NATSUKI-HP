# 図解計画 2026 — 文章中心のサイトから、視覚的に理解できるポートフォリオへ

**作成**: 2026-08-11 / **状態**: H-08 実装済み（基準実装）。残りは未着手。

このドキュメントは2部構成。
前半が **どこを図解すべきかの分析**、後半が **サイト共通の Diagram Design System（DDS）**。

---

## 0. 現状診断

サイト全体を読んだうえでの所見。

### 良いところ

- 記事の中身が濃い。**数字が実測で、失敗が正直に書いてある**。図解する素材としては理想的
- 一覧ページの `metric`（44.2% → 5.8% など）は既に強い視覚要素として機能している
- ミニマル・エディトリアルの規約が効いていて、図を足しても崩れない土台がある

### 弱いところ

- **記事本文が「文字の壁」になっている**。外観検査AIは約6,000字、Fusionは約5,500字。
  いずれも1画面に文字しかない状態が延々と続く
- **記事の一番いい部分ほど、文章では伝わっていない**。
  「同じマスク処理でも、かける場所で結果が正反対になる」「門は、門が見ている対象しか守らない」
  ——どちらも**構造の話**であり、本来は文章より図が速い
- **数字が本文に埋もれている**。19.6時間の内訳、過検出率の5段階の推移、異常スコアの分布。
  すべて図にできる形で記録があるのに、地の文の中に流れている
- **5つのプロジェクトが独立して並んでいる**。実際には共通の主題（正しさを先に確定させる／
  依存を減らす／AIに任せる範囲を線引きする）でつながっているのに、その関係が見えない
- トップとAboutの「3本柱」が**3カラムの並列**で終わっている。
  金型設計・AI・Web が互いにどう関係しているのかが、このサイトで最も伝えるべき差別化点なのに図がない

### 図解の総量に関する注意

**1記事あたり3〜4図を上限**にする。それ以上入れると読者は図を飛ばし始め、
「図が多いサイト」にはなっても「理解できるサイト」にはならない。
現状の work-hub-tools が2図。他の記事も同程度〜4図に収めるのが妥当。

### H-01. 評価指標の欠陥 ― 混同行列で「何を見ていなかったか」を示す

| **なぜ図か** | これは**指標が見ている範囲の欠落**という空間的な話。文章だと2〜3回読み返す必要があるが、混同行列の4象限のうち2象限しか見ていなかったことを塗り分ければ一瞬で伝わる。記事全体の前提になる節なので、ここで詰まると以降が全部つらい |

### H-03. ドメインシフト ― 分離できないという事実を分布で見せる

|---|---|
| **対象** | `/projects/gaikan-kensa-ai` 「実験室では勝てるが、現場では負ける」節 |

### H-08. 3本柱の関係 ― 並列ではなく循環

| 項目 | 内容 |
|---|---|
| **対象** | `/`（トップ）Pillars節 および `/about` 3本柱節 |
| **現在の説明** | 金型設計 / AI開発 / Web開発 を3カラムで並列に説明 |
| **なぜ図か** | **このサイトで最も伝えるべき差別化点が、いま一番弱く表現されている**。3つは並列ではなく、「現場で課題を見つける → AI/Webで解く → 現場に戻して確かめる」という循環。実際、5つのプロジェクトは全部この循環の上に乗っている。並列のカラムはその構造を消してしまっている |
| **図の種類** | 関係図（循環） |
| **含める要素** | 3つの領域／間をつなぐ矢印に「何が渡っているか」を置く（現場の課題 → 手法 → 検証結果）／各領域から実際のプロジェクトへの線（外観検査AI・Fusion自動化・work-hub・花製作所） |
| **理解してほしいこと** | 3つを別々にやっているのではなく、1つの循環として回している。だから現場で使えるものが作れる |
| **実装** | React + SVG。トップはヒーロー下の帯、Aboutはヘッダー直下に配置 |
| **優先度** | **High** ／ **実装済み**（`app/components/diagrams/work-cycle.tsx`） |

**実装時の決定（2026-08-11）**

- 主題は「現場 → 技術 → 現場」。**3つの技術を持っているという見せ方は禁止**
- 技術ノードは中身が入れ替わる前提。現在のスタックは「いまの手段」として従属させる。
  将来技術が増えても図が壊れないこと
- ステーション：01 現場で見つける／02 技術で形にする／03 現場で確かめる。
  03→01 の弧に「新しい課題が出る」、輪の中心に「手段は入れ替わる。変わらないのは、この順序で回すこと。」
- **カラムで組まない**。並列に見えた瞬間に主題が壊れるため、閉じた輪で描く
- Aboutでは既存の3本柱を `Current Means`（02の中身）として位置づけ直した

## 3. Diagram Design System（DDS）

サイト内のすべての図が従う規約。既存のミニマル・エディトリアル規約の延長として設計する。

### 3.1 4つの原則

1. **図は説明の一部であって、装飾ではない**
   文章の言い換えは作らない。「文章だと2回読み返す情報」だけを図にする。
   図を消したときに記事が成立しなくなるなら、その図は正しい。

2. **1図1メッセージ**
   図を作る前に「読者に持ち帰ってほしい一文」を書く。書けないなら、その図はまだ作らない。
   本ドキュメントの各候補にある「理解してほしいこと」がその一文にあたる。

3. **図の中に文章を置かない**
   図には番号バルーンだけを打ち、名称と説明は凡例（HTML）に持たせる。
   モバイルでSVG内の文字が潰れるための措置であり、同時にスクリーンリーダーで読める図になる。

4. **数字は記録から取る**
   図のために丸めない、推測で形を作らない。分布の形が分からないなら、分かっている値だけの数直線に落とす。
   （伏字ルールは図の中でも同じく適用する。社名・製品名・社内パス・金額は載せない）

### 3.2 トークン

既存サイトのCSS変数をそのまま使う。**図のために新しい色を足さない。**

| 用途 | 値 |
|---|---|
| 主線・図形の輪郭 | `currentColor`（= `--foreground`） |
| 補助線・弱い要素 | `currentColor` + `opacity 0.4〜0.55` |
| 注目させる1系統 | `--primary`（朱。light `17 78% 46%` / dark `17 85% 58%`） |
| 面の塗り | `hsl(var(--background))` のみ。**線を切るためだけに使う** |
| 罫線・境界 | `--border` |
| 凡例の説明文 | `--muted-foreground` |

**朱は1図につき原則1系統**。経路なら1本、値なら1つ。2つ以上を朱にすると強調が消える。

**禁止**：グラデーション全般／紫〜青紫の配色／色数を増やして系列を区別すること
（系列は線種・位置・番号で区別する。色は「ここを見ろ」にだけ使う）。

### 3.3 線と形

viewBox の幅を 800 とした場合の基準値。

| 種類 | 値 |
|---|---|
| 主線（機器・境界） | `strokeWidth 1.6〜2.0` |
| 補助線（つなぎ・寸法） | `1.1〜1.3` + `opacity 0.4〜0.55` |
| 越える境界 | 破線 `strokeDasharray="10 8"` |
| 寸法補助線 | 破線 `"2 3"` |
| ハッチング | 45°・`strokeWidth 0.7`・`opacity 0.22`。**囲い／別領域／仮想環境を示すときだけ** |
| 角丸 | 機器 2〜3px、端末 11〜12px。それ以外は角のまま |
| 矢印 | 三角のみ（8×8）。線の端に付ける。装飾的な曲線矢印は使わない |

トップページの製図モチーフ（`die-section.tsx`）の作法に合わせる。断面のハッチング、
番号バルーン、引き出し線——製図の語彙を共通言語にする。

### 3.4 文字

| 場所 | 規約 |
|---|---|
| 図の中 | **番号バルーンのみ**。IBM Plex Mono。viewBox幅の3%以上（800幅なら24px以上） |
| 凡例 | 本文と同じ Noto Sans JP。`text-sm md:text-base`（名称）／`text-xs md:text-[13px]`（説明） |
| FIG番号・系列名 | `font-mono` + `tracking-[0.2em]` + `uppercase`、`text-[10px] md:text-xs` |
| 数値 | `font-mono` + `tabular-nums`。改善後の値は朱 |

図の中に「サーバー」「中継プロセス」といった語を書きたくなったら、それは凡例に置く合図。

### 3.5 レイアウトの型（6種）

新しい図を作るときは、まずこの6種のどれかに当てはめる。当てはまらないなら型を増やすのではなく、
図の設計を疑う。

| 型 | 用途 | 該当する候補 |
|---|---|---|
| **Layers** 同心円・入れ子 | システム構成、到達経路、権限の層 | 既存FIG.01, M-02 |
| **Compare** 上下2段の並置 | Before/After、A案とB案 | H-02, M-03, 既存FIG.02 |
| **Sequence** 時間軸のレーン | 処理の順序、同時実行、擦り抜け | M-04 |
| **Matrix** 2軸4象限 | 位置づけ、見落としの構造 | H-01, H-07 |
| **Quantity** 帯・段差・分布 | 構成比、推移、分布 | H-03, H-04, M-01 |
| **Relation** ノードと線 | 関係、循環、分岐 | H-05, H-06, **H-08（基準実装）**, M-06 |

記事本文に差し込む図は共通枠 `Schematic`（FIG番号 → タイトル → 図 → 凡例 → 補足）に収める。
ページの構成要素として置く図（H-08 など）は `Schematic` を使わず、ページ側の見出しとリード文が枠を担う。

**構成の作り分け（H-08 で確立）**
線は SVG、文言は HTML。SVGを `absolute inset-0` で背景に敷き、文言ブロックを
パーセント座標で重ねる。文言ブロックは `bg-background` を持たせて線を切る。
これにより、どの幅でも文字サイズが変わらず、図形だけが伸縮する。
**文言ブロックの幅は rem ではなく % で指定する**（コンテナ幅が `max-w-5xl` と
`max-w-4xl` で異なるため、固定幅だと狭いほうで要素同士が衝突する）。

### 3.6 レスポンシブ規約

- SVGは `viewBox` 固定、`width: 100%`。**図の中身は拡大縮小のみで対応する**
- 横並びが必要な構成は、**640px未満で縦積みに組み替える**（HTML側のレイアウトで持つ）
- **横スクロールは作らない**。入らないなら情報を削るか、型を変える
- 検証は既存手順どおり **幅500pxのスクリーンショット**（headless Chromeの下限が500pxである点に注意）
- **ダーク／ライト両方で確認**。だから `currentColor` と CSS変数しか使わない。
  headless Chrome でのダーク確認は `--blink-settings=preferredColorScheme=0`（0=ダーク / 1=ライト）。
  `--force-prefers-color-scheme` は効かない

### 3.7 アクセシビリティ

- SVGは `aria-hidden="true"`。意味は凡例（HTMLテキスト）が担う
- 色だけで区別しない。朱＋線種＋位置＋番号で二重化する
- 図を消しても記事が読めること（図は理解を速くするが、唯一の情報源にはしない）

### 3.8 ファイル構成

```
app/components/
├── schematic.tsx          共通枠（Schematic / Legend）※実装済み
├── article-diagrams.tsx   キー → 図コンポーネントの対応表 ※実装済み
└── diagrams/              1図1ファイル
    ├── work-cycle.tsx     H-08。**基準実装**。新しい図はまずこれを読む
    ├── system-map.tsx     work-hub-tools FIG.01
    ├── mail-compare.tsx   work-hub-tools FIG.02
    ├── confusion-matrix.tsx   （H-01・未着手）
    └── ...
```

MDXからの呼び出しは既存のまま `<figure data-diagram="キー"></figure>`。

### 3.9 やらないこと

- カード（影・背景色ブロック・過度な角丸）
- グラデーション、特に紫系。いわゆる「AIっぽい」配色
- アイコンライブラリへの依存（線画は自作SVGで描く。`lucide-react` はUIのみ）
- **図をPNG/JPGで貼ること**（後述）
- 1記事に5図以上

## 4. 実装方式 ― なぜ画像ではなくコードなのか

### 4.1 図はすべて React + SVG（または HTML/CSS）で実装する

理由は4つ。

1. **ダーク／ライトに追従する**。画像では両対応にファイルが2倍になり、しかもズレる
2. **文字が潰れない**。画像の中の文字はスマホで確実に読めなくなる
3. **数字を直せる**。過検出率も手戻り率も進行中の値であり、記事は今後も更新される
4. **差分が追える**。図の変更がgitの履歴に残る

単純な構成比や2軸は **HTML/CSS で足りる**（H-04, H-07）。曲線・角度・重なりが要るものだけSVG。

### 4.2 画像生成AIとCCの役割分担

| | 画像生成AI | CC（コード） |
|---|---|---|
| 構造・関係・数値を示す図 | **使わない** | **すべてここ** |
| 記事のサムネイル、抽象イメージ | 適する | — |
| OGPの背景素材 | 適する | — |
| 現場・実物の写真 | **使わない**（後述） | — |

**画像生成AIを今回の目的に使わない理由**：
今回やろうとしているのは「装飾を増やす」ことではなく「理解を助ける」こと。
生成画像は**それらしいが正確でない**ため、仕組みの説明には使えない。
加えて、線画・朱1色という既存のトーンに揃えるのが難しく、サイトの統一感を壊す。

**特に禁止**：現場の様子や実物を生成画像で代用すること。
実績記事の信頼性を直接損なう。写真が必要なら撮影する。撮れないなら図で描く。

### 4.3 現実的な分担 ― Q（Claude Desktop）と CC

図の設計はCCが一人でやるより、**構図をQで先に固めるほうが速い**。

| 工程 | 担当 | 成果物 |
|---|---|---|
| 1. その図で伝える一文を決める | 本人 + Q | 一文（本ドキュメントの「理解してほしいこと」） |
| 2. 型の選定と要素の洗い出し | Q | 型（6種のどれか）＋要素リスト＋凡例の文言 |
| 3. 構図ラフ | Q | **テキストで**（要素の配置・座標の目安・番号の割り当て） |
| 4. SVG実装・レスポンシブ対応 | CC | Reactコンポーネント |
| 5. 表示検証（500px / ダーク・ライト） | CC | スクリーンショット |

**3のラフは画像ではなくテキストで渡す**。画像を読み取ってSVGに起こすより、
座標と要素の一覧をテキストで受け取るほうが正確で速い。
