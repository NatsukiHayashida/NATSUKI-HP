## 2. 反対する点・成立しない点

### 2-1. P0「モバイルでは横長SVGが約295px幅へ単純縮小されている」→ 成立しない

記事内の5枚（H-01〜H-05）は**すべて以前からモバイル専用の縦組みを別に持っている**。
`sm:` で出し分けており、横組みSVGは `hidden sm:block`、縦組みは `sm:hidden`。

```
app/components/diagrams/*.tsx
  <Overlay ratio="1000 / 470" className="hidden max-w-[900px] sm:block">  ← 横組み
  <Overlay ratio="320 / 480"  className="max-w-[320px] sm:hidden">        ← 縦組み（別SVG）
```

390×844 での実測でも、横スクロールは発生していない（`documentElement.scrollWidth === 390`、
はみ出している要素ゼロ）。レビュー時の計測方法の側の問題と思われる。

> 補足：ヘッドレスChromeの `--window-size` はレイアウトビューポートを変えないため、
> `--screenshot` だけで測ると「横にはみ出しているように見える」偽陽性が出る。
> CDPの `Emulation.setDeviceMetricsOverride` を使うと正しく測れる。

### 2-2. H-03「装置を削除し、文字どおりの数直線と二点と閾値だけにする」→ 採らない

**分布の形は記録に残っていた。** 提案は「両端の位置だけで結論は出る」という前提だが、
当時の推論スコアが1枚1行で全部残っている：

```
~/work/iidzka-inspection/results/b7_cpu_rebuild/scores_all.csv （519枚）
```

集計すると、本文より強い事実が出てくる。

| 群 | 枚数 | 最小 | 中央 | 最大 |
|---|---:|---:|---:|---:|
| 学習と同じ日に撮った良品 | 241 | 0.2580 | 0.3013 | **0.3812** |
| 学習と同じ日に撮った不良品 | 178 | 0.3413 | 0.5140 | 0.9054 |
| 別の日に撮った良品 | 100 | **0.5385** | 0.6587 | 0.7899 |

閾値 0.3413。本文の「上端0.38」「下端0.5385」はこの記録と一致する。

そして――**別の日の良品100枚は、閾値の右へ出ただけではなく、不良品の分布の中に丸ごと入っている**。
不良品178枚のうち**108枚（60.7%）は、別の日の良品の最小値より低いスコア**だった。
良品のほうが、6割の不良品より「不良らしく」出ている。

二点と閾値だけの数直線では、この事実が図から落ちる。なので採らず、
**実測のヒストグラムを3レーンのリッジラインで描いた**（スコア軸1本を共有し、閾値の破線が3本を貫く）。
どのレーンが線のどちら側にいるかを見るだけで済むので、単純さは保てている。

### 2-3. 「製図モチーフを削る」→ 部分的に反対

削るべきは**意味を持たない装置**であって、製図の作法ではない。
今回も、寸法線・端末記号・見当（コーナーの丸）・ハッチングは残している。
消したのは、標本ラック・治具・計器・循環ローラーなど**実在しない機構に見える装飾**のほう。

## 3. 実施した作り直し

### H-03 ドメインシフト（`diagrams/domain-shift.tsx` 全面書き直し）

- 実測のヒストグラム3群を、スコア軸を共有した3レーンで描く
- 閾値の破線が3レーンを貫く。レーン1は線の左、レーン2と3は右
- 不良品レーンの足元に朱の寸法線を引き、別の日の良品が占める範囲（0.5385〜0.7899）を示す。
  真下の朱の山とそのままつながる
- `Readout`：`100 / 100` / `0.999` / `0.38 → 0.5385`
- 凡例5項目 → 3項目
- 見出しを「実験室では勝てるが、現場では負ける」→
  **「別の日に撮った良品は、不良品の山の中に入っていた」**（結論を言い切る）
- 旧版の注記「分布の形は記録に残っていないため描いていない」は**誤りだったので削除**

### H-01 評価指標の欠陥（`diagrams/metric-blindspot.tsx` 全面書き直し）

  - 左：4象限に名前が入った盤面。上段だけハッチング
  - 右：同じ盤面。左列（不良と判定した側）に全部が寄っている

### 本文（`content/projects/gaikan-kensa-ai.mdx`）

記録から2つの事実を足した。どちらも図の主張の裏づけになる。

1. **入力側マスクが悪化した理由**（`results/analysis/roi_v1_report.md` §4.2）
   外周80pxの固定マスクが、端にあった圧痕まで塗りつぶしていた。
   欠陥が消える → その不良品のスコアが下がる（例：0.8654 → 0.5997）→
   見逃しゼロを守るため閾値がNG最低スコアまで下がる（0.4330 → 0.3567）→
   それまで良品判定だった80枚が誤検出に転じる。
   **背景を消すつもりの処理が、閾値を経由して過検出を倍近くに増やしていた。**
2. 不良品178枚のうち108枚が、別の日の良品の最小値より低スコアだった件（上記2-2）

## 4. 残っている論点（判断を仰ぎたい）

### 4-1. H-02の見出し「同じマスクでも、かける場所で結果が逆転する」

記録を読むと、2つのマスクは**同じ処理ではない**。

- 入力側：固定ボーダー80px（`run_patchcore_roi.py`）
- 推論後：ワーク領域に沿った動的マスク（`postmask: dynamic_margin25`）

「同じ処理を置く場所だけ変えた」は物語としては効くが、厳密には正しくない。
正確に書くなら「**入力を削ると失うものがあるが、出力を削っても失うものがない**」。
見出しを変えるか、本文で一言ことわるか、いまのままにするか――ここは判断してほしい。
（図そのものは据え置いてあるので、決まってから直す）

### 4-2. H-04 / H-05（CAD自動化の記事）

同じ方針で直せるが、**記事1本ずつ完成させる**という約束があるので手を付けていない。
方向はレビューに賛成：H-04は70/30の帯1本、H-05は外枠と内枠だけ。

### 4-3. サイト全体の文章量

レビューの指摘（記事末尾の `Outcomes & Results` / `Challenges Overcome` / `Key Learnings` が
本文と重複、日本語記事の末尾だけ英語見出し）は妥当。ただしこれは**図ではなく記事構成の話**で、
5記事すべてに効く。図が片付いてから別途まとめて扱いたい。

Approach の文言（「ふつう二人で回る／一人で閉じる」「AIを軸に」）については、
**本人の立ち位置の宣言なので、CCが勝手に薄めるべきではない**と考える。
指摘の趣旨（分業や協働を否定して読まれうる）は理解できるので、直すかどうかは本人の判断に置く。

## 5. 確認方法（次に触るとき用）

デスクトップ／モバイルの実寸確認は、CDPでデバイスエミュレーションしてから撮ること。
`--window-size` だけのヘッドレス撮影はレイアウト幅が反映されず、偽の横はみ出しが出る。

```bash
# scratchpad に置いた shot.mjs / shot-dark.mjs と同じ手順
#   Emulation.setDeviceMetricsOverride { width, deviceScaleFactor: 2, mobile: true }
#   Page.captureScreenshot { clip, captureBeyondViewport: true }
```

ダークモードは `Emulation.setEmulatedMedia { prefers-color-scheme: dark }` で確認。
H-01 / H-03 は確認済み。**塗り（`fill` + `opacity`）はダークで想定より強く出る**ため、
範囲を示したいときは塗りではなく**朱の寸法線**を使うほうが両テーマで安定する（H-03で入れ替えた）。
