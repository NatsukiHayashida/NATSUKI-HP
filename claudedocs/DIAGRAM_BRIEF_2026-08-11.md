# 図案依頼書 — GPT / Gemini 用（2026-08-11 改訂）

**この文書が現行版。** `DIAGRAM_BRIEF_GPT_GEMINI.md` は前提が古いので使わないこと
（「名称は凡例へ回す」という指示が入っているが、その方針は撤回済み）。

**使い方**：「共通の前提」＋依頼したい図1件分の節を、まるごと貼り付ける。1回の依頼につき1図。

返ってきた草案は Claude Code が検証・React化・組み込みを行う。
**GPT / Gemini の成果物は「構図の説明・SVG草案・凡例リスト」の3点セットまででよい。**

## 共通の前提（毎回これを一緒に貼る）

個人ポートフォリオサイトに載せる技術記事の**模式図の設計**をお願いします。
サイトは製造業（冷間鍛造の金型設計）のエンジニアのもので、デザインは
**ミニマル・エディトリアル**。機械製図の作法（細線・罫線・ハッチング）をモチーフにしています。

### いちばん大事な基準（これを満たせない案は採用できません）

**図から名称・ラベル・数値をすべて隠した状態で、次の4つが判別できること。**

1. 何と何を比較しているか
2. どこが問題か
3. 何が変化したか
4. 結論はどこか

文字を消すと意味がなくなる図は、模式図ではなく**フローチャート**です。
**形・位置・範囲・重なり・欠損**で結論を伝えてください。
とくに「結論を文章で大きく書く」のは無効です。その文章を消したら何も残らないためです。

### 出力してほしいもの（3点セット）

1. **構図の説明**（文章）：何をどこに置き、視線をどう動かすか
2. **SVG草案**（SVGのソースコード。**PNGや画像ファイルではなく、テキストのSVG**）
3. **凡例リスト**：名称 → 一行説明。**図が語れないことだけ**を書く（図を見れば分かることは書かない）

### PC用とスマホ用、構図を2つ

サイトはスマホでの閲覧が中心です。**横長の図を縮めると読めなくなる**ので、
**縦に組み替えた別構図**を必ず用意してください。

- PC用：横長（viewBox 例 `0 0 1000 470`）
- スマホ用：縦長（viewBox 例 `0 0 320 480`。**幅320で成立する構図**に組み直す）

「横のものを縦に並べ替えただけ」ではなく、狭い幅で読める構図にしてください。

### 色 — 明暗2つのテーマがあります

サイトには**ライトモードとダークモード**があり、利用者が切り替えます。
**決め打ちの色（`#242424` や `#f4f1ea` など）は使えません。** 明るい背景を前提に描くと、
ダークモードで「黒い画面に白いカードが浮いた」状態になります。

色は次の**3つの役割だけ**で組んでください。実際の値への置き換えはこちらで行います。

| 役割 | 草案での書き方 | 用途 |
|---|---|---|
| 線・文字 | `currentColor` | 線画のほぼ全部 |
| 背景・白抜き | `hsl(var(--background))` | 線を切る、面を抜く |
| 強調（朱） | `hsl(var(--primary))` | **1図につき1つの意味だけ** |

- **新しい色を足さない。** 青緑・グラデーション・紫は使わない
- **強調色に複数の意味を持たせない。**「欠陥」と「失敗側」と「悪化した数値」を
  全部同じ色にすると、その色を見ても何のことか決まりません
- 面を区別したいときは塗りつぶしではなく**ハッチング（斜線）**を使う（製図の断面表現）。
  塗り（`fill` + `opacity`）はダークモードで想定より強く出ます

### 図の中に文字を置かない

viewBoxごと縮むので、スマホで潰れます。**名称はHTMLでSVGの上に重ねます**（こちらで行います）。

- SVGの中には**文字を一切入れない**（見出し・ラベル・数値・「AI」などの文字も含む）
- そのかわり、**名前を置く余白を空けておいてください**。
  どこに何という名前を置くつもりかは、構図の説明に書いてください
- 番号バルーンだけを打って名称を凡例へ回すのも**禁止**です。
  図と凡例を往復させることになり、読むのに一手間かかります

### そのほか

- **矢印と文字を並べただけの図は禁止。** 形のあるものを線画で描く
- **処理の流れを箱で並べない。** 見せたいのは工程ではなく「何が消え、何が残ったか」。
  モデルやAIを箱として描く必要はありません
- カード・背景色ボックスは使わない。罫線と細線で構成する
- **数値・事実の創作は禁止。** 仕様に書かれた数値だけを使う。
  「粒を10個と8個並べて割合を表す」のように、根拠のない数を描くのも創作にあたります
- 会社名・製品名・人名・金額・社内パスは、仕様に書かれていなくても絶対に入れない。
  部品は実物ではなく**汎用の丸物**として描く

## H-07R. マスクの適用位置 ― 受け取った草案（`h-07-mask-placement-pc/mobile.svg`）の直し

いただいた2構図を描画して、実験記録と照合しました。直してほしい点を重要な順に挙げます。

### 先に ― 活かしてほしい点

次はそのまま使いたいので、変えないでください。

- **図の中に文字がない**こと
- **`label-slot-*` のID付き余白**。名前を重ねる位置が分かるので、そのまま活かします
- **`--bg` / `--line` / `--accent` の3役**に色を整理してあること
- **部品の形**（外形の円＋中心穴＋均等配置の小穴）。伏字の条件を満たしています
- **スマホ版が上下2段**であること

### 1. 「何が変わったか」が図から消えています（最重要）

右端に並んだ小さな部品が、**PC版は12個 対 12個、スマホ版は7個 対 7個で同数**です。
2つの経路の結果が**まったく同じ絵**になっており、この図でいちばん見せたい差が消えています。

**小さな部品の格子は、両方とも削除してください。**
数量はHTML側に数値で大きく出すので、絵で個数を表す必要はありません。
根拠のない個数を描くと、事実の創作になります。

### 2. ×と✓の記号を使わないでください

良否を記号で書いてしまうと、図が説明したことになりません
（記号を読んでいるだけで、絵は何も証明していない）。**両方とも削除してください。**

そもそもこの図の結論は「良い／悪い」ではありません。
**「欠陥が消えたか、残ったか」**です。それが絵で分かれば記号は要りません。

### 3. マスクは黒塗りではなく、外周の帯です（前回から未修正）

**(a) 色が違います。** いまは線と同じ濃い色の矩形（`opacity=".84"`）ですが、実際は
**背景の平均色で塗りつぶし**ています。黒塗りは
「モデルが黒い領域を新たな異常パターンとして学習するリスクを避けるため」
**意図的に避けた**手法なので、図が実際と反対のことを描いています。
`--bg`（背景色）で塗りつぶし、輪郭だけ細線で示してください。

**(b) 位置が違います。** いまは部品の中央あたりを四角が覆っていますが、実際は
**画像の外周を一定幅で塗りつぶす帯**（額縁状）です。
失敗の実体は「**端**のほうにあった欠陥が、外周の帯に飲み込まれて消えた」ことなので、
中央を覆う描き方だと因果が成立しません。

**欠陥印は部品の外周寄りに置き、その位置が帯の内側に入るようにしてください。**

### 4. 「欠陥が消えた」パネルがありません

いまは黒い矩形が半透明なので、**欠陥が下に透けて見えたまま**です。
肝心の「消えた」が絵に出ていません。

第1経路には、**マスクを適用した後の絵**を1つ置いてください。
そこには部品はあるが、**欠陥印が無い**。これがこの経路の結論です。

### 5. 異常マップの「前」と「後」が判別できません

第2経路の右側（マスク後）で、**点線の枠の中に背景の点がまだ残って**います。
消す前なのか後なのかが読めません。

- マスク**前**：四隅に背景の点がある。部品の上に欠陥の反応がある
- マスク**後**：四隅の点が**無い**。欠陥の反応は**残っている**

また、いまは**朱の欠陥が点線の枠にかかって**いて、マスクされる側に見えます。
欠陥の反応は、除去範囲から**明確に外して**ください。

### 6. PC版も上下2段にしてください

いまPC版は左右比較ですが、**上下2段**にしてください。
スマホ版と同じ骨格になるので、読み方を2回学ばずに済みます。

### 7. スマホ版のレイアウトが重なっています

×／✓の丸が、小さな部品の列の最後に重なっています。
（1と2で両方とも削除されるので、結果的に解消するはずです）

### 8. 処理を表す箱は要りません

⊕の付いた箱が両経路にありますが、見せたいのは工程ではなく
「**何が消え、何が残ったか**」です。削除して構いません。

### 名称を隠したとき、こう読めるのが目標です

```
第1経路  部品に欠陥印がある → 外周の帯が欠陥印にかかる → 欠陥印が消えている
第2経路  部品に欠陥印がある → 四隅と欠陥に反応がある   → 四隅だけ消え、欠陥は残っている
```

強調色（朱）の使い方には2案あります。どちらでも構いませんが、**1つの意味に固定**してください。

- **案A：朱＝削る範囲**。第1経路は朱が欠陥印にかかり、第2経路はかからない。差が一目で出ます
- **案B：朱＝欠陥・異常信号**（いまの案）。この場合、削る範囲は `--line` の細線とハッチングで表す

### この図で使ってよい事実と数値

記事本文に書いてある範囲です。ここに無い数値は使わないでください。
**数値はHTML側に置くので、SVGには描かないでください**（余白だけ空けてください）。

| 事実 | 値 |
|---|---|
| マスクなし（ベースライン）の過検出率 | 44.2% |
| 入力画像にマスクをかけたときの過検出率 | 72.4% |
| 推論後の異常マップにマスクをかけたときの過検出率 | 20.8% |
| 背景の反応が出る場所 | 画像の四隅（部品が写っていない領域） |
| 制約 | 両方とも「不良品の見逃しゼロ」を守った上での比較 |

因果（凡例に書く内容。図には描かない）：
外周の帯が端の欠陥まで塗りつぶす → その不良品の異常スコアが下がる →
見逃しゼロを守るには閾値をその最低スコアまで下げるしかない →
閾値が下がった分だけ、それまで良品と判定できていた製品が不良側に落ちる。

### 「同じ処理を別の場所に置いた」とは書かないでください

記録上、2つのマスクは同じ処理ではありません。

- 入力側：画像の外周を一定幅で塗りつぶす、**固定の帯**
- 推論後：部品の輪郭に沿って対象外を判定から外す、**部品の形に沿ったマスク**

形が違うので、上下を鏡像のように対称に描くと事実と食い違います。言いたいのは次のことです。

> **入力を削ると、失うものがある。出力を削っても、失うものはない。**
